OEE Management & Loss Analysis

This module teaches how to calculate and interpret Overall Equipment Effectiveness, OEE, a single measure built from three separate factors, Availability, Performance, and Quality, and how to structure those losses into a ranked view so the site can see exactly where its output is actually being lost. It builds directly on downtime data the site may already be capturing, and extends it to cover losses that a simple stop log alone never shows: running slower than it should, and producing units that don't count as good output even while the machine is technically running.

What it takes

Time
Calculating a first OEE figure for one asset, once basic downtime data exists, typically takes a day or two. Capturing Performance and Quality losses properly, if they aren't already tracked, takes longer, often a couple of weeks of deliberate observation to build a reliable baseline.

Common questions

FAQ

We already track downtime. Isn't that basically OEE?

No, and this is the single most common gap this module closes. Downtime data alone answers "was the machine running or not," which only covers Availability, one of three factors. It says nothing about a machine running slower than its designed rate, or producing units that don't pass quality even while technically up. Both are entirely invisible to a stop log. See Pro section 2.

What's the actual formula?

OEE equals Availability multiplied by Performance multiplied by Quality. They multiply, not add, which is deliberate: a genuinely weak factor drags the whole number down regardless of how strong the other two are, rather than being averaged away and hidden. See Pro section 13.

Why does the exact definition of "available time" matter so much?

Because different definitions of what counts as Planned Production Time, which stops are excluded as planned, can move the resulting OEE number substantially without any real change in performance. A generous definition produces a comfortable, less honest number. This module requires that definition be explicit and documented, not assumed. See Pro section 2 and section 4.

Our site already reports an OEE figure. Do we need to redo it?

Audit it first rather than assuming it's wrong or right. Check the existing figure against the same three boundary questions this module uses: what counts as Planned Production Time, what's the reference cycle time, and what counts as a good unit. If the existing definition doesn't hold up, that's worth knowing, and it isn't an accusation about anyone's honesty, just a correction going forward. See Pro section 5's decision fork and section 17.

Why might our OEE number go down once we start measuring it properly?

Because an informal or generous existing definition often makes the number look better than real performance actually is. A lower, honestly calculated number isn't bad news about performance getting worse, it's better visibility into performance that was already this way. See Pro section 17.
