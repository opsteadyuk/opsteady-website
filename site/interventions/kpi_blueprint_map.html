Common questions

FAQ

What if different people on my site would name different numbers as the one that matters?

That disagreement is the actual finding, not a delay before the real work starts. Resolve it before building anything: a tree built on the wrong top number has to be redone from scratch. See the decision logic in section 18, fork 2.

I've already got something that looks like a KPI tree. Do I still need to build one from scratch?

No, treat it as an audit instead. Bring the existing version to the paper session and run every link through the same five steps as a claim to test, not a fact to copy, rather than starting from a blank page. See section 4 and section 18, fork 1.

Do I need to know a link is definitely true before I put it on the tree?

No, and forcing that is a common way this goes wrong. Mark what you're confident about as known, what you believe but haven't checked as assumed, and what you genuinely can't say as unknown. Expect roughly one in four assumed links to turn out wrong once you test them. A tree with no question marks has almost certainly been guessed rather than built. See section 5, and the "built in a meeting room, never tested" failure in section 16.

What if a branch traces all the way down to something, but nobody can actually change it this shift?

That's the most common failure, and the hardest to spot, because the tree looks finished. Apply the floor test literally: name the person and the shift who can see that measure and act on it, not the report it arrives in. See section 5 for the full test, and section 16 for how this failure shows up in practice.

What if my site doesn't have good data to test the links against?

A first pass that's mostly unknowns is a valid, useful result, not a failed attempt. It converts a vague sense that "we need better data" into a specific, scoped list: these measures, at this level, feeding this number. See section 14 for the low-data variant and section 18, fork 3.
