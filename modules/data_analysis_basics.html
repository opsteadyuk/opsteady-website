Data Analysis Basics

Know which tool to reach for, and stop guessing when two versions of the same event don't agree.

Overview

Most sites end up holding data they don't quite know how to read: a defect count nobody's ranked, a spec sheet with limits and no sense of whether the process can actually hit them reliably, a cluster of scrap that might be happening in the same spot every time or might not, and — sooner or later — two numbers about the same event that don't match, with no way to settle it except an argument. The problem isn't a missing skill so broad it needs a course, it's that nobody's ever been shown which specific tool answers which question.

This module teaches four short, specific techniques, each for exactly one question: Pareto (already living inside Downtime Tracking & Pareto Pack) for ranking causes when there are more problems than time to fix them all; process capability, Cp and Cpk, for whether a process can reliably hit a spec, not just today but as a matter of course; hotspot or defect mapping for whether a problem has a physical pattern; and reconciling conflicting data sources for settling a live disagreement between two real numbers. The reconciliation problem has a named cause: two people can count the same thing correctly by their own definition and still get different numbers, because nobody agreed what actually counted as "the event" before either started counting.

Done properly, someone reaches for one of these four tools before arguing from instinct when a new disagreement or unclear dataset shows up, and reconciliation specifically stops being skipped because it's awkward — it happens as a matter of course when two numbers disagree, not only when someone insists.

At a glance
Time

Pareto: none, it's covered fully inside Downtime Tracking. Cp/Cpk: about 30 minutes once you have 20 to 30 measurements already recorded. Hotspot mapping: an hour to set up the outline, then a few minutes a day to mark it. Reconciliation: as long as the actual disagreement takes to talk through, usually well under an hour once both sides bring their definitions rather than just their numbers.

Who's involved

Whoever already owns the relevant data. Reconciliation specifically needs both sides of the disagreement in the room, not one side relaying the other's position secondhand.

For your own site, decide: who's allowed to change a spec limit, versus who can only flag that the process isn't meeting the one that exists; when two data sources disagree, who has the authority to declare which definition becomes the one going forward; and who reviews a hotspot map once it's built, and how often it gets refreshed.

What you'll need

No statistics background required — each tool is a short, specific method, not a course; unfamiliar terms are explained from nothing in the companion training document. The working file is four short reference sheets plus a combined quick-reference rather than one workbook: a Process capability sheet (formulas, a blank worked example, the note that there's no single universal Cpk target), a Hotspot mapping sheet (a blank outline template and a cluster-or-scatter reading guide), a Reconciliation sheet (a two-column side-by-side template — what each source counts, where its clock starts and stops, the agreed definition once settled), a Pareto pointer to Downtime Tracking's own workbook, and the four-line "which tool do I need" quick-reference.

Before you start

Introduce each tool at the point it's actually needed, not as a batch training session covering all four at once — a hotspot map gets built when a location-pattern is suspected, Cp/Cpk gets pulled out when a spec exists and nobody's checked the process against it, reconciliation happens the moment two numbers disagree, not on a schedule.

Work out first whether this is a live disagreement between two numbers or a single dataset you're trying to read: for a single dataset, pick the tool from the four-line list based on the question you're actually asking; for a disagreement between two sources, always run reconciliation first, even if you think you already know which side is right — confirming the assumption is faster than defending it later.
