Running a Project

Delivering a real project without learning how to run one the hard way, on the fly, under pressure.

Overview

Someone capable often gets handed a real project with no structure for scoping it, planning it, or knowing when it's actually finished. Projects quietly expand because "out of scope" was never written down anywhere, and milestones get set once at the start and never revisited as the real work reveals what the plan missed.

This module is the minimum a genuine first-timer needs, not a project management methodology course: a one-page plan written before starting, not after — a clear objective, a scope with an explicit out-of-scope, milestones with real dates, named ownership confirmed directly with each owner, and an agreed definition of done before work starts. It's deliberately distinct from two neighbouring modules: a project plan and a change plan are different documents doing different jobs, so it stays separate from Managing Change That Sticks (E2) even where a piece of work genuinely needs both; and it teaches the general skill of running a project, upstream of Kaizen Event Planner & Charter Pack (P7.2), which applies the same discipline specifically to a focused improvement event.

Done properly, the one-pager gets referred back to at each milestone, not filed and forgotten after being written, and the project finishes against what it defined as done, not against a vague sense that it's probably wrapped up.

At a glance
Time

An hour or two to write the first one-pager properly, considerably less once the habit is familiar.

Who's involved

Whoever's running the project, plus a named owner for each milestone, not always the same person as whoever's leading overall. For your own site, decide: what real project is already sitting on the desk, waiting for structure; what's genuinely in scope, and what needs naming as deliberately out; and who owns each milestone, and have they actually agreed to it.

What you'll need

One real project already in mind, not a hypothetical example — this only earns its place once it's run against something genuinely on the desk. The working file, E7_Project_One_Pager_and_Milestones.xlsx, two tabs: a Project one-pager (objective, in scope, explicitly out of scope, and what done looks like, refusing to count itself finished while the out-of-scope half is empty, and flagging an objective that needs two sentences as a project that probably needs splitting into two) and a Milestone tracker (one row per milestone — what it is, the owner, a real date, whether that owner confirmed it directly, status and days overdue, reporting a milestone whose owner hasn't confirmed it until they have).

Before you start

Check first whether there's a real project already in mind, or only a hypothetical one — a hypothetical project teaches the mechanic but nothing sticks, so use a real one from the first attempt if at all possible. Write the one-pager before any work starts, not partway through once the shape of the project has already drifted without anyone deciding it should, and tell everyone named as a milestone owner, agreeing to what they're actually responsible for before the project starts, not discovering it partway through.
