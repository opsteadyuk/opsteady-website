Kanban & Pull System Design

This module turns the capacity and inventory work already done elsewhere in the P4 pillar into a practical pull system, a defined loop where material or work only moves because the next process signalled it actually needs more, not because a schedule, forecast, or habit says to make it. It teaches a physical or basic-digital kanban loop, a card, an empty container, a supermarket location, or a FIFO lane, that a team can run and adjust itself, without a project team or new software.

What it takes

Setup timeMapping current push points and designing one loop usually takes a few days. Calculating a defensible starting quantity from real usage data, rather than guessing, is where most of that time goes. Trialling and adjusting the loop before locking it as the standard typically takes one to two weeks of real running.

Common questions

Do we need software or a full MRP overhaul to run this?
No. A physical loop, cards, containers, marked floor locations, is the standard starting point and is enough for most connections. A basic-digital equivalent is a later refinement, not a prerequisite. See Pro section 2.
How do we work out the right kanban quantity?
From real average usage and the real replenishment time for that specific connection, not a round number or a figure copied from elsewhere. Start from the calculation, then adjust based on what the trial week actually shows, since ordinary variation on a real process rarely matches a spreadsheet exactly. See Pro section 5 and section 15.
What if we set the pull loop up and the downstream process still starves sometimes?
Check the quantity first: it's usually too tight for the real variation in demand, not a sign the pull concept itself has failed. Adjust upward based on trial evidence rather than reverting to the old push schedule. See Pro section 9's first failure.
Do we need to know our site's bottleneck before doing this?
Yes, or at least have a working understanding of it. A pull loop designed without reference to the real constraint can starve it or overload it, undermining the whole flow regardless of how well the loop itself is designed. See Pro section 10 and section 18's third fork.
What happens to the old schedule once the pull loop is running?
It needs to genuinely retire for that specific connection, not run alongside the new signal indefinitely. A loop competing with a parallel schedule leaves people unsure which one to actually trust, and that uncertainty is one of the most common ways this module fails. See Pro section 16's third failure.
